Receipts are four-phase: `pending` (receipt + oracle named, nothing called) → `spawning` (appended **and fsynced immediately before Popen** — the fence) → `launched` (pid + detach line, after spawn returns) → `done`. The start marker is a **sibling file, not a child of the envelope path** (r5-F001): `<ledger>/lanes/<id>/<stage>.<op_id>.started`. Claude dispatch goes through **`dispatch_wrapper.py`** (committed in the skill dir, batch 2) rather than a `sh -c` chain (r6-F001, r6-F003): the wrapper's own argv carries `--op-id <op_id>`, so the id stays in the process table for the dispatch's whole lifetime instead of vanishing at `exec`; it creates the marker and **fsyncs both the file and its directory** before spawning `claude` as a supervised child (stdout to the envelope path), waits, and fsyncs the envelope on exit — the same supervision shape `run-codex.sh` already uses. Recovery (r4-F002, r5-F002): `pending` with no `spawning` → provably nothing was called → safe to re-plan. `spawning`/`launched` without an envelope → the reality oracle is a **process-table scan for the op_id in the wrapper's argv**: found → adopt, record pid, keep waiting; not found **and** no durable marker → affirmative negative — the wrapper fsyncs the marker before it spawns the model, so an absent marker after a crash means the model was never spawned (r6-F001 closed the lost-marker crash case); not found, marker present, no envelope → **park, never re-dispatch**. Codex QA receipts rely on the runner's own supervision: the per-attempt state dir is the oracle and `CLODEX_INVOCATION_ID` rides the runner's environment; adoption reads the state dir plus the detach pid. Oracle present+parses → settle. Ship §8's discipline, copied.
