# AI-driven frontend design: what the evidence says, and what it changes in `jp-frontend-design`

Date: 2026-09-02 · Author: Atelier thread (Claude, Fable 5.1) for Johnny Palumbo · Status: research memo, ends in an upgrade spec (§8)

Scope: the state of AI-driven frontend design as of September 2026, read against one question — **how does a coding agent produce distinctive, high-craft UI when the human gives only a one-line ask, and what separates the workflows that do from the ones that produce generic output?** A second question rides along because the test bench (a read-only ops deck) already has an acceptance eval: **how can the agent evaluate design output mechanically, on itself, before a human sees it?**

Method: seven parallel research lanes, each a fresh-context subagent with web search and fetch, each told to grade every claim **(a)** verified from a primary source, **(b)** secondary or reported, or **(c)** inference, and to write "no source found" rather than invent. The seven lane files ship beside this memo in `research/lanes/` and carry ~350 numbered sources between them; this memo cites the ~70 that carry its conclusions. Where a lane read a page I could re-fetch, I re-fetched it (the Anthropic Opus 4.8 and Fable 5.1 prompting pages, the general prompting best-practices page). Web-search budget for the session ran out mid-way through the last lanes; those closed with direct fetches and list their gaps.

Lanes: R1 agentic design tools (79 sources) · R2 tokens and design-system extraction (69) · R3 screenshot-critique loops (61) · R4 slop convergence and prompting (63) · R5 mechanical design evals (76) · R6 the ops-dashboard genre (58) · R7 practitioner workflows with coding agents (61).

---

## 0. Bottom line

1. **The current skill's order is the consensus order.** Brief → tokens → reference analysis → one hero screen → screenshot critique → scale out is, step for step, what Anthropic's own plugin skill, its bundled `artifact-design` and `/design` skills, Impeccable, Lovable's design guidance, and thirteen independent practitioner write-ups converge on [1][2][3][4][5][6]. Nothing in the sequence is debunked. What the evidence changes is the *mechanism inside each step* and the *gates between them*.

2. **Distinctiveness is decided in the first two steps and only protected afterwards.** The critique loop removes measurable defects; it does not invent a direction. Every controlled result on visual self-correction shows modest, front-loaded gains that plateau by round 2–3 [7][8][9]; every source on identity says it comes from subject grounding plus one signature element, written down before code [1][2][10].

3. **Bans relocate the attractor; they do not create variety.** Anthropic now documents this about its own models: "Generic instructions ('don't use cream,' 'make it clean and minimal') tend to shift the model to a different fixed palette rather than producing variety" [11]. Its cookbook admitted banning Inter produced Space Grotesk [12]. The one controlled eval of the frontend-design skill text (50 prompts, blind Opus 4.5 judge, 75% win rate, p = 0.006) came largely from pairing every NEVER with an INSTEAD and deleting instructions the model can't act on [13]. The slop list survives only as a *paired* list.

4. **The diversity mechanism that works is enumerating distinct directions in one context and picking one.** Anthropic prescribes it ("propose 4 distinct visual directions … bg hex / accent hex / typeface — one-line rationale. Ask the user to pick one, then implement only that direction") and says to use it instead of temperature [11]. The mechanism is Verbalized Sampling: enumerating options recovers ~67% of pre-alignment diversity, 1.6–2.1×, quality preserved, and larger models benefit more [14]. Best-of-N from the same prompt does not recover diversity [15]. Nielsen's 1996 parallel-design study gives the human-side number: best-of-4 +56%, merged +152% [16]. Directions should be *rendered* where cheap (Lovable renders three throwaway previews on the first UI prompt and skips the step when the prompt already specifies fonts, colors, brand) [17].

5. **Tokens store taste; they do not originate it.** No controlled tokens-vs-none study exists. The nearest (SpecifyUI) shows a structured spec beating prompt-only Stitch on style consistency 5.52 vs 4.18 and layout consistency 4.99 vs 3.73 [18]. shadcn is the most tokenized system on the web and "famously look[s] the same" [19]. What tokens demonstrably fix is cross-generation drift. Models will not self-enforce them (DesignBench: 0.24% component reuse in React) [20], so a rogue-literal check belongs in the loop. Every tool that gets on-brand output pairs tokens with **prose rationale** (Stitch DESIGN.md: "Tokens give agents exact values. Prose tells them why") [21].

6. **The screenshot loop works because the screenshot is external feedback, and it has a ceiling.** Intrinsic self-correction without an external signal degrades output [22]. With a render: ReLook +3 points from the reflection loop alone, humans preferred loop output 50% / worse 20%, trajectories converged to ~2 rounds [7]; Amazon's CITL +6.2% after cycle 1, plateau at 3, and *keeping the best cycle* was worth +17.8% vs +8.7% for last-cycle [8]; VisRefiner declines by turn 5 without best-of selection [9]. VLMs are blind to specific properties: DiffSpot finds Claude Opus 4.7 at 38.9% on single-CSS-change detection, with line-height recall ~4%, border-radius 13%, gradients ≤27% [23]. Scripts own those. The critic must be a fresh context (self-preference bias is causal [24]; Anthropic: "so the agent doing the work isn't the one grading it" [25]), and "find 10 problems" is a demand characteristic — cap, don't floor [25].

7. **Cold VLM aesthetic judgment is at chance; anchored judging is strong.** UIClip put GPT-4V at 51.6% on pairwise UI-quality judgments vs designers [26]; ArtifactsBench's checklist-anchored judge reaches >90% pairwise agreement with experts [27]; synthetic heuristic evaluation with MLLMs found 73–77% of usability issues vs 57–63% for five practitioners, strong on layout, weak on conventions [28]. The deck's four glance questions are exactly the anchor that works. Pairwise judging needs both orderings and a fresh judge (position bias flips top-1 on 16–39% of prompts) [29][30].

8. **On a utilitarian surface the failure is wrong register, not "generic."** Anthropic: the house style "will feel off for dashboards, dev tools, fintech, healthcare, or enterprise apps" [11]. The genre has real rules — Few's pitfalls (excessive precision, nothing highlighted because everything is, color overuse) [31]; cockpit law reserving red and amber for warning and caution [32]; NASA's display standard ("Color must be used to convey meaning, and not for decoration") [33]; Carbon's three-of-four rule for status (symbol, shape, color, type) [34]. Distinctiveness on an ops surface is precision and structure that encodes meaning, with at most one signature element that carries information [11][35][36].

9. **What the current skill misses** (R7 §6, corroborated across lanes): no step 0 that reads the existing system; a brief too thin for a one-line ask; no diversity mechanism or named axis for the three directions; directions as text, not renders; a critique loop with a floor but no ceiling, run in the builder's own context; slop tells as prose only; a stale banned-font list; no written rationale beside tokens; no rule to ship alternates beside the deliverable when autonomous; no evidence-before-done rule.

10. **Evidence quality, honestly.** Controlled results exist for the loop (four papers), for diversity prompting (Verbalized Sampling, Nielsen), for VLM judge reliability (UIClip, ArtifactsBench, position-bias papers), and for one skill text (PR #210). Everything about tokens, references, personas and community skills is vendor policy, practitioner heuristics, or before/after screenshots. Six community skills with 24k–124k GitHub stars publish zero controlled evals. Persona prompts have no measured capability effect [37].

## 1. The core question: where distinctiveness comes from

### 1.1 Why output converges

Post-training compresses diversity: RLHF "significantly reduces output diversity compared to SFT" [38], and the driver is *typicality bias in preference data* — annotators favor familiar text; 51.6–60.8% of preference pairs across five base models and four datasets favor the higher base-model-probability response [14]. Anthropic's own diagnosis is "distributional convergence … safe design choices — those that work universally and offend no one — dominate web training data" [39]. The fiction-side twin: 11 words occur in 88.3% of 20,000 generated stories across four models, traced to shared preference data, not training text [40]. That is why the slop look is the same in Claude, GPT and Gemini output, and why "looks professional" as judged by a typical rater *is* the typical look.

Homogenization is a population property: individual outputs get better while the set converges (Doshi & Hauser: AI-assisted stories 8.9–10.7% more similar to one another while individually rated higher) [41]. The current skill's slop test — "would a generic version of this prompt produce the same direction?" — is precisely a crowding test at the population level, and the literature says that is the right kind of test. Keep it as the gate.

### 1.2 What moves the model off the attractor

Ranked by evidence strength (R4 §3):

1. **A concrete positive spec before code** — hex palette, named faces, radius, layout concept, motion timing. "The model follows explicit specs precisely" [11]. A positive spec is the only instruction that removes the attractor rather than relocating it; negation is read and obeyed but specifies nowhere to go [11][12][42].
2. **Enumerate N distinct directions in one context, pick one, implement only that** [11][14][16]. Rendered where cheap [17]. Magic Patterns confines variants to *consequential* axes (layout, density, theme) and forbids trivial ones [43]; the `/design` skill: "each exploring an axis you can name … five shades of one aesthetic is no choice at all. Decision fidelity is not deliverable fidelity" [3]. Impeccable derives seven candidate worlds from the audience's cultural world, requires ≥3 material families, deals the direction by dice roll "to defeat the category default," and keeps a labelled conventional "canon" exit [4].
3. **Close the loop with a check the model can read**, graded from a fresh context [25] — see §3.
4. **Anti-pattern list with every NEVER paired with an INSTEAD** [13]. Deterministic where possible (Impeccable's 61 detectors on hooks; the 16 tells catalogued by Developers Digest: colored left borders on cards, badge-above-H1, icon-top card grids, stat rows, all-caps labels, italic-serif hero word) [4][44].
5. **Subject grounding + one signature element + compact plan reviewed against "could this apply to a similar project?"** [1][2]. Bans and rubrics remove slop; subject grounding is what supplies identity. Anthropic's `artifact-design`: "carry at least one detail only this subject would have — its real units and scales, its document conventions, its terms of art — as content, not ornament" [2].
6. **Reference screenshots or named aesthetic families instead of adjectives** — Figma: models "default to safe, average-looking output when a prompt includes only vague or simplistic adjectives like 'clean' or 'modern'" [45]; source code beats a screenshot when available [3].
7. **A written design file in the repo** (DESIGN.md / design plan) — buys consistency and on-brand; it is distinctive only if what it encodes is [21][46].

Weak or unproven: personas (no capability effect on factual tasks, register-only [37]); temperature (weak, and Sonnet 5 rejects it) [11][15]; "make it not look AI-generated" alone [11]; instructions the model can't act on ("never converge across generations") [13]; star counts as evidence [R4 §4]; Design Arena leaderboards (they measure preference on a shared prompt, which rewards typicality) [R4 §4].

### 1.3 What the tools do mechanically

The comparison table is in R1. The patterns that generalize to a coding-agent skill:

- Every tool that produces on-brand output front-loads a written spec in **two layers**: tokens plus prose. Bolt's docs: documentation alone "produce[s] a theme rather than a true design system" [47]; Stitch DESIGN.md is YAML tokens + markdown rationale [21]; Figma Make uses Guidelines.md + tokens.md [48]; Lovable's leaked prompt: "Start with the design system. This is CRITICAL" [49].
- **Directions are rendered, not described.** Lovable: three lightweight HTML previews on the first UI prompt, ≤6 steering rounds, skipped when the prompt already specifies fonts/colors/brand [17]. Stitch and Uizard generate variants per screen. Claude Design does *not* do parallel variants [50].
- **Generation-side constraints are negative and numeric.** v0's newer leaked prompt: exactly 3–5 colors, ≤2 font families, no purple/violet, no gradients, no blobs, no emoji icons, all color via tokens; plus a `GenerateDesignInspiration` tool called *before* code on vague asks [51][52] (leaked; multiple mirrors agree).
- **Token enforcement is mechanical.** Lovable scans every generation for raw color literals and off-scale values and auto-retries [53]; v0 DS 2.0 refuses tokens "not verified from the sources" [54].
- **References become extracted rules, then are discarded.** Stitch extracts DESIGN.md from a URL; v0 extracts tokens from repos/Figma; Magic Patterns passes referenced screens' *code*; Figma MCP returns `get_variable_defs` plus a screenshot [R1 §6].
- **None of the SaaS builders self-screenshot** (v0, Lovable, Bolt, Replit, Stitch). Only Cursor and the coding-agent skills do [R1, R3 §1.4].
- **The one harness with measured originality gains** is Anthropic's planner/generator/evaluator: Claude "scored well on craft and functionality by default … but on design and originality, Claude often produced outputs that were bland at best" until the evaluator weighted those higher; self-evaluation "confidently prais[es] the work" [55].

## 2. Tokens: store, not source

Verdict on "taste lives in the tokens file": overstated. Rewrite as *taste is decided in the brief and the design plan, then frozen into tokens so it survives every later generation.*

- **Coherence: supported, indirectly.** SpecifyUI's structured spec (color + role, radius + style label, grid spacing, tone, layout rhythm) beat prompt-only Stitch by ~1.3 points/7 on style and layout consistency, p < .001 [18]. DesignRepair found v0's guideline violations cluster in spacing, text and color — the token layer — and repaired them at 89% precision against a system knowledge base [56]. Drift across generations is the documented failure a persisted file counters (dMaya: "The button on screen one is not the button on screen four … Claude does not see its previous generations" [57]; FronTalk's "feature forgetting" [R2 §3.5]).
- **Distinctiveness: not supported.** The most tokenized system on the web is the one that "famously look[s] the same" [19]. Distinctiveness enters through deliberately chosen *values* and the non-token layer: layout concept, hierarchy stance, signature element, motion posture [1].
- **Enforcement must be mechanical.** DesignBench: component reuse 0.24% in React; alignment is 42.2% of repair samples [20]. Tailwind v4's `--*: initial` or a rogue-literal grep is the practical form.
- **The minimal set that carries taste** (triangulated across Radix's five knobs, shadcn's role set, DTCG types, DESIGN.md, SpecifyUI, Anthropic's "4–6 hex + 2+ type roles + layout + signature"): 6–10 color roles as surface/on-surface pairs; two faces + scale ratio + weight pair + display tracking + body leading (type is the highest-leverage carrier, 11 independent sources [R7 T6]); base unit + a **density multiplier** (no standard has a density token; Radix `scaling` is the only mainstream knob [R2 §Q2]); one radius stance; elevation stance; one duration pair + one easing pair; and four **prose** lines that are not tokens: layout concept, hierarchy stance, signature, refused defaults.
- **Reference analysis.** Vision is reliable for *relations* (hierarchy, density, rhythm, tone, layout pattern) and unreliable for *exact values* — "current LLMs often struggle with precise color extraction," palette relevance rated lowest of all outputs [58]. Global profile first, then regions [18]; section-wise decomposition raises degradation-detection F1 0.46 → 0.78 [59]; read computed styles when a URL exists. Analysis-to-abstraction (extract the system, discard the composition) is the only path to a non-derivative token set; cloning yields a page (GPT-4V clones judged exchangeable with the reference 49% of the time — good fidelity, which is exactly why it is the wrong tool for "could not be mistaken for anyone else's") [60].

## 3. The screenshot-critique loop: what it does and doesn't do

### 3.1 Evidence it works, with sizes

| Study | Effect | Rounds |
|---|---|---|
| ReLook (Tencent, Oct 2025) [7] | +3.0 on ArtifactsBench-Lite from the reflection loop alone; human check: loop output preferred 50%, worse 20%, tie 30% | converged to ~2, capped at 3 |
| CITL (Amazon AGI, Apr 2026) [8] | judge score +6.2% (cycle 1) → +7.8% → +8.7%; **best-of-cycles +17.8%**; multi-dimensional judge agreed with humans 69.5% vs 48.5% single-score | plateau after 3 |
| 1D-Bench (Alibaba, 2026) [61] | render-success 63.6% → 93.2% with diff heatmap + logs per round | 3, early stop |
| Design2Code (Stanford, 2024) [60] | one self-revision round: GPT-4V human win+tie 82% → 85%; **no gain** for Gemini 1.0 or open models | 1 |
| VisRefiner (Feb 2026) [9] | 92.0 → 92.9 peak at turn 3 → **declines to 92.6 by turn 5**; best-of-turns 94.2 | — |
| Huang et al., ICLR 2024 [22] | self-correction *without external feedback* degrades performance | — |

Reading: 2 rounds default, 3 max; keep the best round, not the last; accept a revision only if nothing regressed (ReLook's "forced optimization" was worth +2 points alone [7]).

### 3.2 Blind spots

- **Property-specific.** DiffSpot (4,400 UI pairs, one CSS change each): Gemini 3.1 Pro 47.2%, Claude Opus 4.7 38.9%, GPT-5.4 38.3%; line-height recall median 4%, border-radius 13%, gradients ≤27%; alignment shifts and text substitutions caught well; some models hallucinate changes on unchanged pairs [23]. 85% of real screenshot-to-code errors are element *omission* [62].
- **Resolution.** Claude downscales to 1568 px long edge (2576 on 4.7+); a 1920×1080 full-page shot lands 12 px text at ~9 px. Crop regions, label images, put images before text [63]. The Fable 5.1 prompting page recommends giving vision work a crop-and-zoom tool for dense images [64].
- **Priors over pixels.** VLMs defer to expectation on familiar-looking objects [65]; a standard-looking card grid may be reported as fine because it is *expected* to be fine. A critique loop run by the same model will not flag its own house style unless the checklist names it [57].
- **Taste.** MLLM-as-UI-judge correlates with humans on aesthetic pleasure and hierarchy but near zero on ease of use [66]; UICrit zero-shot critiques were only 13.1% valid, +55% with few-shot exemplars, and human designers still won 81% of the time [67]. **No source found** that a "senior product designer" persona improves critique validity; the weight belongs on exemplar critiques and the checklist [37][67].
- **What a static screenshot can't show:** hover/focus/active states, motion, below-the-fold, cross-browser.

### 3.3 Screenshot vs code

DesignBench: for edit and repair, "code-only input consistently outperforms image-only input"; localization accuracy only 0.45–0.77 [20]. Interaction2Code: adding a text description to the screenshot raised CLIP +80% on failure cases; region marking +32% SSIM [68]. DesignRepair's 92% recall came from running a code stream and a Playwright-extracted rendered-property stream in parallel [56]. Synthesis: the render is ground truth for *what is wrong*; code/DOM/computed styles are ground truth for *where and by how much*; scripts own the sub-pixel properties the VLM will not see.

### 3.4 Prompt patterns, ranked

1. Checklist-guided multi-dimensional scores, not a single verdict [27][8].
2. Reference + own render + code, labelled, in one prompt [60][63].
3. Text alongside pixels (OCR'd copy, the brief, the tokens file) [60][68].
4. Few-shot exemplar critiques beat role prompts [67].
5. Localize with zoomed patches or selectors (IoU 0.18 → 0.36) [69].
6. Name the failure taxonomy in the prompt: occlusion, crowding, text overlap, alignment, contrast, overflow, omission [20][62].
7. Regression gate on each revision; keep-best [7][8][9].
8. Fresh-context critic [24][25].
9. Cap the issue count, don't floor it — "A reviewer prompted to find gaps will usually report some, even when the work is sound" [25].

### 3.5 Budgets in practice

Anthropic `artifact-design`: "Write, look once, publish … Don't build a test loop around your own file" [2]. Impeccable: one inspection round + one confirm, "two rounds is the ceiling … Open-ended self-QA burns the user's money," then a fresh-context finish reviewer [4]. aidesigner: two passes max [R7 T3]. design-loop: autonomous until all five criteria ≥4/5 twice, plateau stop after 3 [70]. The evidence and the practice agree: minimum 1, maximum 2 batched rounds, a third only on a measurable high-impact issue.

## 4. Evaluating design mechanically

### 4.1 Instruments, from weakest to strongest

- **Cold VLM aesthetic judgment: at chance.** UIClip: GPT-4V 51.6%, LLaVA-1.6 54.6% on pairwise UI quality vs designers; a small fine-tuned CLIP hit 75.1% [26]. AesEval-Bench: GPT-5 0.73 on judgments, <0.20 on localizing the flaw [71]. Never ask "which is prettier"; never ask for bounding boxes.
- **Computational aesthetics: ~half the variance at best** (Reinecke 2013 ~50%; Miniukovich 2015 up to 49% webpages, 32% apps) [72]. Use as lint, not score.
- **Human critique's own reliability problem.** Any two evaluators agree 5–65% across 11 studies; five find ~75% of problems, one ~35% [73]. So craft critique runs ≥3 independent passes, unions findings, never gates alone.
- **Automated accessibility: cheap with a documented ceiling.** 57% of issues by volume (Deque, 13k pages) but the best tool found 41% of GDS's 143 planted barriers and 29% were missed by every tool [74][75]. Contrast 83% automatable; focus order and meaningful sequence 98–100% manual — the agent's scripted Tab-walk *is* the manual check. axe's `target-size` is still experimental; compute from bounding rects [76].
- **Checklist-anchored VLM judging: strong.** ArtifactsBench >90% pairwise agreement with experts, 94.4% ranking consistency with WebDev Arena [27]; synthetic heuristic evaluation 73–77% issue recall vs 57–63% for practitioners [28].
- **Pairwise with controls: the highest-leverage judge use.** Position bias is systematic and strongest when candidates are close in quality — the polish regime [29]; rubric-position bias flips top-1 on 16–39% of prompts, fixed mostly by shuffling 3–5 orderings [30]; self-preference is causal [24]. Both orderings, ≥3 runs, majority rules per ordering (a win needs a majority in each, a regression a majority in either; otherwise a tie — refined at batch 12 from the earlier "disagreement = tie"), judge never sees the generating transcript.

### 4.2 Glance time

Web attitudes settle by 2 s, but purpose identification of a *complex* page keeps improving through 10 s [77]; most smartwatch interactions last <5 s and bar/donut comparisons resolve <300 ms [78]. So recognition-class questions (which agents, alive?) should pass fast; comprehension-class (what did they do, cost / anything wrong?) legitimately need the full 10 s and are the ones that fail. No study measures glance comprehension on ops dashboards specifically. Real UI attention is top-left and text-biased, not color- or size-driven, and generic saliency models fit UIs poorly until trained on UI data (NSS 0.66 → 0.84) [79] — so put the answers to Q1–Q2 top-left. The squint/blur test has no controlled validation (NN/g and LukeW endorse it as practice); it is cheap and stays as a hierarchy probe only, with a drop-if-unused rule [R5 §1.2].

### 4.3 The rubric (R5 §4, adopted)

Three layers with different trust levels. **A** is deterministic and gates. **B** is a fresh-context vision pass with bias controls that gates only on the concrete questions. **C** is critique — informative, aggregated, never a sole blocker.

**A — mechanical (Playwright/DevTools — a browser automation that can render the page, capture it and run scripts in it: computed styles, a keyboard Tab walk, axe-core; Lighthouse when available, its absence recorded — which is what step 0's preflight confirms, a screenshot tool alone cannot run this layer; both viewports 1400×900 and 390×844, both color schemes):** A1 no horizontal overflow at 390 (report at 320; WCAG Reflow) · A2 text contrast ≥4.5:1 / 3:1 large · A3 non-text contrast ≥3:1 for status marks and borders · A4 smallest rendered text ≥ 11 CSS px (Apple's 11 pt Caption 2 — *erratum 2026-09-03: an earlier draft wrote 14.7 px by converting typographic points; at viewport scale 1 (`width=device-width, initial-scale=1`) one iOS point is one CSS pixel. Lane file R5 §A4 keeps the original 14.67 derivation as the record of what was first adopted — this memo and the rubric supersede it*); body ≥16 px · A5 tap targets ≥24×24 (gate) / 44 advisory · A6 focus visibility via a scripted Tab-walk · A7 reduced-motion honored · A8 heading structure, landmarks, accessible names, zoom not disabled · A9 clipping/truncation inventory on glance-critical text · A10 line length ≤80 ch on prose · A11 no color-only status encoding · A12 design-system lint (distinct font sizes ≤5, weights ≤3, spacing on scale, colors from the declared palette — advisory) · A13 axe floor, plus Lighthouse when available (its absence a recorded deviation, never a silent skip; never presented as "accessible").

**B — vision (fresh context, captures + the surface's questions — B3 also a one-line direction and the A advisories, never the plan, tokens, hard-gate results or answers, ≥3 runs, both orderings, options shuffled):** B1 answer-the-questions glance test — a gate only where a fixture-backed acceptance eval exists (scored against the data fixture at ≥ 90 % of question-runs, 11/12 for four questions × three runs, no question below 2/3; the above-the-fold crop must answer the recognition questions alone), and elsewhere an advisory probe on the generic questions the design plan can answer — what is this (the plan's subject/job), what matters now (its hierarchy stance); what changed / what should I do only when the surface carries state or a call to action — scored against the plan's stated answers and reported, never gated · B2 degraded-input glance (50% and 25% downscale; "name the three things you see first"; "which region looks wrong?") · B3 pairwise vs the previous accepted form (never merely the previous round's rejected candidate), judged blind — neutral X/Y labels assigned at random per call, the captures copied under neutral file names into a fresh directory, and nothing in the handoff — path, file name, caption, metadata or prompt text — naming a round, a date or a form, or saying which version is which; three calls with the revision shown first and three with the previous form first, labels drawn independently, a verdict per dimension per viewport (the rubric §C's eight dimensions — glance chart choice and papercuts n/a without a chart or interaction, an n/a neither a win nor a regression) (phone and desktop judged separately), a second panel on the other color scheme whenever the revision touched a color token or scheme-specific CSS — otherwise the A gates and §B5 cover that scheme — the orchestrator keeping the mapping and mapping verdicts back — anchored on B1 and A-advisories, no regression allowed in either ordering (a regression = a majority of the three calls in either ordering preferring the previous form; one dissenting call is not one; ties never are; every majority is counted per viewport — a regression at either viewport is a regression, and a win needs its majorities in each ordering at one viewport on one dimension), a no-issue round closing without a panel with the previous accepted form standing, a polish round (no measurable fix in it) closing only on a win — a majority of the three calls in each ordering preferring the revision on at least one dimension — and all ties meaning no regression and no win · B4 defect-checklist scan asking for judgments and element *names*, never coordinates · B5 theme parity (the same B1 on the other color scheme, with B1's gate-or-advisory status).

**C — craft critique (≥3 independent passes, union, severity 0–4, ranked, never a sole gate):** hierarchy · spacing rhythm · typography · color · copy · glance chart choice · papercuts · direction fidelity — each with 1/5 anchors (R5 §4C), scored 1–5 (glance chart choice and papercuts n/a without a chart or interaction); every issue carries a stable key (the CSS selector or element name plus the defect class), a severity 0–4, a location (image + region, or a CSS selector), a MEASURABLE or JUDGMENT tag and a token-first fix; passes are unioned by key — an issue's severity is the highest any pass gave it, its frequency the number of passes that named it — and ranked by severity × frequency.

Gates, in the loop's causal order (§8.1 step 4): A hard gates → C (critique; its applied fix list, re-gated and recaptured, is the candidate — the hero's round-0-clean capture itself gated by B1/B5 before it is frozen as the baseline, a failure repaired in step 3 and the gate re-run) → B1 (on every full-loop candidate after its fix list, and on the low-stakes path whenever the surface has a fixture-backed eval — there after B3, on the kept form; a gate only where a fixture-backed eval exists, an advisory probe elsewhere) → B5 (the same B1 on the other color scheme, same status) → optional B2 (50 % downscale) → B3 no-regression → keep the best round. Log every judge call with ordering and run index.

## 5. The utilitarian surface: rules of the ops-dashboard genre

Anthropic draws the line itself: the house style "reads well for editorial, hospitality, and portfolio briefs, but will feel off for dashboards, dev tools, fintech, healthcare, or enterprise apps" [11]. Jakob's Law and NN/g's complex-application guidance ("Removing nonessential elements can be equally or even more effective at making important information visually salient") [80], and Linear's 2024 redesign ("reduce visual noise … increase the hierarchy and density"; less chrome color for "a more neutral and timeless appearance") [35], all say the escape from generic on a tool is precision, not decoration. The "generic version" to beat is *default shadcn dashboard*.

The genre's rules, each sourced (R6):

- **The dashboard is read at a glance, in three steps**: see the big picture → focus on what needs attention → drill in to act [31]. On a phone the first viewport carries the overview; everything below is Few's "gateway."
- **Few's pitfalls the current deck commits**: excessive precision ("$3,848,305.93 rather than … $3.8M" — the tester's "tokens are useless" is this pitfall exactly); ineffective highlighting ("because everything … is visually prominent … nothing in particular grabs your attention. When this happens the dashboard has failed"); color overuse [31].
- **Alerts only when abnormal.** 14 CFR 25.1322: red for warning, amber for caution, and red/amber "for functions other than flightcrew alerting must be limited" [32]. NASA-STD-3001 App. F: "Color must be used to convey meaning, and not for decoration"; an additional cue beyond color for critical information; labels left of values; units on every number; fixed-width digits for numbers, proportional for prose; mixed case for non-acronyms; 6:1 contrast (10:1 preferred); flash reserved for immediate attention [33]. Fourteen colored status words on a healthy page is the anti-pattern a cockpit forbids.
- **Status = shape + word + color.** Carbon: of symbol, shape, color, type "at least three … must be present"; consolidated status takes the highest-attention color; filled icons carry more weight than outlined [34]. WCAG 1.4.1 forbids color alone. Okabe-Ito vermillion/orange/bluish-green over pure red/green; Grafana: "avoid red and green color combinations" [81][82].
- **Worst-wins banner in plain English.** Statuspage computes "All Systems Operational" → "Minor Service Outage" → "Partial System Outage" from component states [83]; PagerDuty severity vocabulary supplies the words; severity first, then the noun, then the plain-language consequence [R6 §1.6].
- **Numbers.** Tabular lining figures, right-aligned, same decimals, headings aligned like their data, no zebra, no vertical rules, no outer frame [84]. `tnum` is supported by only 16% of web fonts, so system faces (SF, Segoe) or `ui-monospace` are the safe path [R6 §2.1]. Monospace for identifiers and numeric columns only; proportional for prose — all-mono removes the size/weight hierarchy pitfall #10 needs, and "the content must genuinely warrant the density" or it reads as costume [85].
- **Type scale on phone**: 17 px band text, 15–16 row primaries, 13 secondary, 11–12 only for tracked labels; nothing below 11 px [86]. Tracked caps (+5–12%) for section labels only [87].
- **Dark and light from one token set** via `light-dark()` + `color-scheme` (Baseline 2024) [88]; dark surface a deep gray, not #000; desaturate status hues in dark; Linear derives ~100 variables from three inputs in LCH [35]; Tailscale: don't invert, use semantic tokens [89].
- **No-JS devices that survive**: native `<details>`/`<summary>` (state dies on each meta-refresh, so the server decides what is open) [90]; `title` is *not* disclosure ("highly problematic for people using touch-only devices") [91]; word-sized CSS bars and state strips (Grafana's state timeline as a flex row of colored spans; charts.css proves "No JS = no rendering" charts) [92]; `<meter>` for value-in-range; relative time is *free* on a 15 s re-render, absolute in mono beside it for anything older than the hour and on all problem lines [93]. W3C F41: meta-refresh fails WCAG 2.2.1; the only no-JS honor is a `?refresh=0` pause link [94].
- **Money is a table lookup** when calls are metered [95] — but see the deck's constraint below.
- **Rams**: "unobtrusive," "honest," "as little design as possible" [96] — the brief for a read-only deck.

**Deck-specific constraint found in the ledger (read-only query, 2026-09-02):** 78 rows since 08-21; every call sits on a subscription lane (claude-a/claude-b via `claude -p`, codex-cli, local); no metered-lane call has ever happened; and `claude-cli` rows carry ~1 input token per call, so the dominant lane's input counts are not real. Dollars from this ledger would be a false precision. The honest budget measures available without new credentials are calls per lane/account, per-agent escalations against the policy cap (40/day, readable from `policy.yaml`), and the literal line "metered: $0 — no metered calls." Weekly-ceiling percentage needs `ccusage`, which the deck's user cannot run; say so rather than fake it.
